# P3 任务系统父子任务插件：实现成本与可能性评估

> 评估日期：2026-10-30 | 评估对象：`@local/dsh-task-list`（`F:\DSH\projects\DSH任务系统重建计划`）

## 0. 结论摘要

**不需要新插件。** 问题出在现有 `task_write` 的「描述 + 校验」两层：它允许任意平铺，且从不提示该拆子任务。改现有插件即可，成本约 **1–2 人日**（描述规则 + 软校验 + 测试）；用独立插件去 `pre-execute` 拦截同一个工具，属于重复建设，不推荐。

## 1. 现状证据

`F:\DSH\projects\DSH任务系统重建计划\index.js`：

- `task_write` 的 description（L162–168）只说「整表替换 / 保留 id / 缺失视为撤回 / 四态 / blocked」，**没有一句关于父子结构的要求**。
- schema（L169–193）里 `parentId` 是可选字符串，**没有任何结构约束**（顶层数量、父任务是否必须有子任务、层级深度）。
- execute（L195–204）只做 `mergeAgent` + `writeTaskState`；`mergeAgent`（`lib/task-store.js` L222–267）最后调 `assertValidTree`，而它只校验：父存在、不是自己、不成环（L384–400）。**平铺完全合法**。
- 对比 `todo_write` 的描述有「Add one todo per concrete step before you start」这类行为引导，`task_write` 没有对应文案。

## 2. 根因

模型一次性排大量父任务、不设子任务，是三个因素叠加的**最低成本解**：

1. **整表替换**：每次都要提交全量，拆父子意味着多一层 id 引用与排序，平铺更省 token、更省思考。
2. **描述不引导**：工具没说「顶层是阶段、执行项必须是子任务」，模型自然按「一条任务一个条目」处理。
3. **没有门禁**：结构校验只保「树不坏」，不保「树合理」，所以平铺永远不会失败。

也就是说：**不是模型不听话，是接口没有表达「什么样的树算合格」。**

## 3. 方案对比

| 方案 | 做法 | 成本 | 风险 | 结论 |
|---|---|---|---|---|
| **A. 改现有 task-list（推荐）** | 改 `task_write` 描述 + 在 execute 后加软校验 | 1–2 人日 | 低；不动 UI/存储 | **推荐** |
| B. 独立插件 pre-execute 拦截 | `tools/pre-execute` 检查 `task_write` 参数，违规拒绝 | 1–2 人日 | 中：逻辑与 A 重复，且要跟随 task_write 的 schema 变化 | 备选 |
| C. 只改提示词/白皮书 | 在 AGENTS.md 加「先拆子任务」规则 | 0.1 人日 | 高：已实测无效（模型接入时仍平铺） | 否决 |
| D. 新工具 `task_plan` | 先提交父任务大纲，再逐层展开 | 3–5 人日 | 中高：模型仍可能不用，且与 task_write 双轨 | 不推荐 |

## 4. 方案 A 的设计要点

### 4.1 描述层（低成本、立竿见影）

在 `task_write` description 里加三段规则（措辞要短）：

- 顶层任务 = 阶段/大块交付，不是执行步骤；超过 3 个顶层时先问「能不能归到几个阶段下」。
- 每个顶层任务至少要有 1 个子任务；一个子任务 = 一次可验收的动作。
- 只有两层的项目结构（现有面板只渲染两层，不要造第三层）。

### 4.2 校验层（软优先）

**软校验**（推荐先做）：`mergeAgent` 成功后检查：

- 新增的顶层任务（不在旧列表里的）数量 > `maxFlatTopLevel`（默认 3）且这些顶层任务全无子任务 → 在返回文本里追加 warning，**不拒绝**。
- warning 文案示例：`Updated ... (warning: 4 top-level tasks without subtasks — group them under phase parents and add child tasks)`。

为什么软而不是硬：

- 现有列表里已有平铺任务（本会话 19 条就是），硬拒绝会让 agent 无法更新自己的列表；
- 模型看到 warning 后通常会在下一次 `task_write` 里补结构；
- 若要硬约束，应只对「本次新增的顶层任务」生效，并提供 `allowFlat: true` 逃生参数。

**可选硬模式**（第二阶段）：配置 `structurePolicy: "soft" | "strict"`，strict 时拒绝并返回结构化错误，方便团队统一。

### 4.3 兼容与测试

- 旧数据：只对新增顶层任务计数，不追溯历史。
- 单测加 3 条：新增 4 个平铺顶层 → 出现 warning；4 个顶层但挂了子任务 → 无 warning；3 个以内 → 无 warning。
- 前端零改动（只改返回文本与描述）。

## 5. 成本估算

| 项 | 估算 |
|---|---|
| 改描述 + 软校验 + 返回文本 | 0.5–1 人日 |
| 单测 3 条 + 手工验证 | 0.5 人日 |
| 可选：strict 配置 + 逃生参数 | +0.5–1 人日 |
| **合计** | **1–2 人日** |

## 6. 风险

1. **软约束可能被忽略**：模型若连续忽略 warning，需要升级为 strict（配置项，不破坏默认）。
2. **整表替换的固有成本**：即使拆了子任务，每次仍要提交全量；这是既有设计，不在 P3 范围。
3. **面板只渲染两层**：如果模型造三层，现有 `removeSubtree`/渲染会如何处理需确认（HANDOFF 说「只做两层」），描述里必须写死「最多两层」。
4. **与 `todo_write` 并存**：`todo_write` 已 disabled，无冲突。

## 7. 结论

**P3 不立项新插件，改 `task-list` 现有 `task_write`：描述加结构规则 + 软校验 warning（可选 strict）。** 成本 1–2 人日，风险低，不动存储与 UI。独立插件方案（pre-execute）只在「不想改自研插件代码」时才选。

若用户确认，实施顺序：
1. 改 description（3 段规则）；
2. 加软校验 + warning 文本；
3. 补 3 条单测；
4. 重启/重载后，用一次真实任务提交验证 warning 出现与结构改善。
