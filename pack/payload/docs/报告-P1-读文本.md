# P1 读文本统一插件：实现成本与可能性评估

> 评估日期：2026-10-30 | 宿主：dsh 0.2.1-rc.3 | 评估口径见 `HANDOFF-插件评估.md` §2

## 0. 结论摘要

**不需要自研。生态里已有一个功能几乎完全覆盖需求的现成插件 `dsh-fs-encoding`（v1.5.2），装上即用，成本约 0.5 人日（安装 + 验收）。**

- 现状根因已从源码确认：`read` 只走严格 UTF-8 解码，非 UTF-8 直接 `FS_NOT_TEXT`；写/编辑也只认 UTF-8，BOM 不保真。
- 现成插件在 agent 作用域层 shadow 了 `read`/`write`/`edit`/`grep` 四个工具，工具名与参数不变，模型调用习惯零改动；支持 19 种编码、BOM/换行符保真、字节级无损回写、非 ASCII grep 不再静默漏报。
- 自研（替换 fs 后端或写后置修复插件）预计 3–5 人日，且很难超过现成插件的能力面，**性价比不成立**。
- 唯一需要做的决策是：直接采用该插件（推荐），还是先在本机做一轮 GBK/UTF-16/BOM 样本验收再采用。

## 1. 需求边界

要解决（用户描述）：DSH 读文本时的各类错误——报错、乱码、字节当字符——即使白皮书第⑥条已有编码规范，仍需临场解决。

具体拆成四个可验证的问题：

| # | 问题 | 期望 |
|---|---|---|
| 1 | 读非 UTF-8 文件（GBK/GB18030/Big5/Shift-JIS）直接报错 | 能读，或给出明确候选编码并支持显式重读 |
| 2 | 带 BOM 的 UTF-8 文件被读写后 BOM 丢失 | 读保留、写还原，不擅自增删 |
| 3 | 写/编辑后文件被悄悄转成 UTF-8（编码漂移） | 按原编码写回，不静默损坏 |
| 4 | grep 搜非 UTF-8 文件时命中行显示乱码或静默 0 条 | 命中行显示真实内容；不确定时给候选而非漏报 |

不解决（边界外）：
- PowerShell/终端管道的编码问题（白皮书第⑥条那类，属于执行层规范，不是文件读工具）。
- 字节与字符的度量口径混用（如 SHA256 按字节、`String.length` 按 UTF-16 码元）——插件只能减少编码转换类错误，不能替调用方统一度量语义。
- PDF/音频/视频读取（原生也不支持）。

验收标准：用真实样本（GBK .txt、Big5 .txt、UTF-16LE 带/不带 BOM、UTF-8 带 BOM、CRLF 文件）各跑一遍读→改→读，内容与字节编码不变。

## 2. 现状证据（宿主源码）

### 2.1 读：严格 UTF-8，非 UTF-8 直接失败

`dsh-fs-local/lib/index.js`（从 app.asar 提取）：

- L329–330：`function notTextError(...)` → `new FsError('cannot ${verb} "${path}": invalid UTF-8 text', "FS_NOT_TEXT")`
- L332–340：`decodeUtf8` 用 `new TextDecoder("utf-8", { fatal: true }).decode(buffer)`，解码抛 `TypeError` 即转 `FS_NOT_TEXT`
- L370–376：`readWholeText` 先检查前 `BINARY_SAMPLE_BYTES`（8192）是否含 NUL，含则 `FS_NOT_TEXT` "binary file"，然后 `decodeUtf8`
- L452–474：流式读同样是 `TextDecoder("utf-8", { fatal: true })`

结论：**没有编码检测、没有 GBK/UTF-16 回退、没有 BOM 语义**。`dsh-tool-fs` README 的「已知限制」也写明：**`read` 只处理 UTF-8 文本文件**（README.zh.md L252）。

### 2.2 写/编辑：同样只认 UTF-8

- `writeText`（fs-local L865–883）直接按 UTF-8 落盘；`editText`（L884–901）先用 `decodeUtf8` 读原文。
- BOM 不被保留：读进来时 `TextDecoder` 默认剥掉 BOM，写回时按 UTF-8 无 BOM 写，原文件若带 BOM 会丢。

### 2.3 字节/字符口径

- `read` 的 `readMaxBytes` 按 UTF-8 字节截断（`lineByteSize` 用 `Buffer.byteLength`，tool-fs L32–34），`readMaxLineLength` 按字符截断（`line.length`）。两个上限混用本身没错，但调用方容易把行截断提示（字符）与字节上限（字节）当成同一回事。
- 这解释了「把字节当字符」类困惑的一部分；根因不在工具，而在编码转换与度量口径没有统一出口。

## 3. 现成实现：`dsh-fs-encoding` 1.5.2

来源：npm `dsh-fs-encoding`（MrWeiCodes，MIT，17★，2026-10-17 更新，已被 awesome-dsh-plugin 收录）。本次已下载 tarball 核对源码与清单（`F:\DSH\temp\dsh-fs-encoding\package`）。

### 3.1 它怎么接管

`cordis.patch.yml` 只有一行 `insert`，插件在 **agent 自己的作用域层**注册 `read`/`write`/`edit`（以及 `grep`、`insert`、`undo_last_edit`、`str_replace_editor`），按「最近层优先」**shadow** 掉 preset 内置工具：

- 不替换 `ctx.fs`，读仍走 `ctx.fs.readBytes`；
- 写复用公开的 `fs/write-intent` + `fs/observed` 事件闸门和 sandbox 策略 API；
- 沙箱围栏、先读后改、版本校验、diff 展示全部保留；
- 卸载即恢复原生工具，不修改宿主代码。

### 3.2 能力面

| 能力 | 说明 |
|---|---|
| 编码 | UTF-8（含 BOM）、UTF-16LE/BE、UTF-32LE/BE、GBK/GB18030/GB2312/CP936、Big5/CP950、Shift-JIS/CP932、EUC-KR/CP949、Windows-125x 全系、ISO-8859-1 |
| 读 | 默认严格 UTF-8；非 UTF-8 报 `E_NOT_TEXT` 并列出候选与各自解码效果，模型用 `read({..., encoding: "gbk"})` 重读；可开 `autoGuessEncoding` 自动猜 |
| 写/编辑 | 首次读取确定编码，之后按原编码写回；BOM/CRLF 原样保留；目标编码表示不了的字符**拒绝写入**而非写 `?` |
| grep | 非 ASCII 模式按候选编码分别搜索并用 submatch 裁决；不会把 UTF-8 文件误判成 legacy；拿不到 subprocess 服务的部署不装 grep，原生保持 |
| 额外工具 | `insert`（按行号插入）、`undo_last_edit`、`str_replace_editor` |
| 服务 | 提供 `fsEncoding` 服务（`tryDecode`/`decode`），其他插件可复用同一套判定 |

### 3.3 已知限制

- 默认**不猜**无 BOM 的非 UTF-8 编码（安全优先），模型会多一次「按提示重读」的调用；开 `autoGuessEncoding: true` 可自动，但极短文件仍可能要求人工从候选中选。
- 与任何在**同一层**注册同名工具的插件互斥；本机 profile 只有宿主内置 `tool-fs`（宿主角层），不冲突（已核对 profile 的 `cordis.patch.yml`：`tool-fs`、`tool-fs-search` 均在 preset 层）。
- 会话内编码记录存内存，重启后首次读取重新识别（不落盘）。
- UTF-32 的 grep 走 JS 兜底，正则语法是 JS 的；无 BOM 的 UTF-32 搜不到。
- 第三方单维护者项目，长期维护不确定，建议锁版本。

## 4. 候选方案对比

| 方案 | 做法 | 工作量 | 风险 | 结论 |
|---|---|---|---|---|
| **A. 直接采用 dsh-fs-encoding** | `dsh plugin add dsh-fs-encoding`，重启 | 0.5 人日（安装 + 样本验收） | 第三方依赖、升级跟随上游 | **推荐** |
| B. 自研 fs 后端 | 继承/重写 `ctx.fs` 后端，加编码检测 | 5–10 人日 + 持续跟随 910 行 fs-local 上游 | 高：替换核心服务、契约面大、升级易碎 | 否决 |
| C. 自研后置修复插件 | `tools/post-execute` 拦截 read 的 `FS_NOT_TEXT`，自行解码替换结果 | 2–4 人日 | 中：依赖内部事件替换语义，只救读不救写；需验证失败结果可否替换 | 备选 |
| D. 自研增强工具 `read_text` | 新工具带 `encoding` 参数，与 read 并存 | 3–5 人日 | 中：工具重复、模型选择成本、观测事件要对齐 | 备选 |
| E. 只靠提示词/白皮书 | 现已如此 | 0 | 已被用户实测证伪 | 否决 |

**自研（C/D）只在以下条件成立时才值得做**：现成插件在 0.2.1-rc.3 上装不上、有阻断性 bug、或需要覆盖它不支持的编码/行为。否则重复造轮子。

## 5. 成本估算（采用现成插件）

| 项 | 估算 |
|---|---|
| 安装与重启 | 10 分钟 |
| 样本验收（GBK / Big5 / UTF-16 / BOM / CRLF 各 1 个，读→改→读） | 0.5 天 |
| 配置调优（`autoGuessEncoding` 是否开、`maxFileBytes`） | 0.5 小时 |
| 长期维护 | 跟随上游版本，每次 DSH 大版本升级后抽验一次（0.5 天/次） |
| **合计** | **约 0.5 人日（一次性）+ 每次升级抽验** |

对比自研：C+D 组合 5–9 人日，且能力面大概率不如现成（19 编码、grep 裁决、BOM/CRLF 保真都是现成的）。

## 6. 风险

1. **第三方信任**：MIT、可审源码；建议 pin 1.5.2，不自动升级。风险等级：低。
2. **版本兼容**：peerDeps 覆盖 `0.1.5-alpha` ~ `0.2.1-alpha <0.3.0`，当前 `0.2.1-rc.3` 在范围内；但它是「按层 shadow 工具」的实现，DSH 若改工具注册层级语义会受影响。风险等级：中，升级时抽验。
3. **模型行为变化**：默认不猜编码，模型需要多一次重读调用；若模型不照提示做，会表现为「还是读不了」。可用 `autoGuessEncoding: true` 缓解，但极短文件仍会要求候选选择。风险等级：低。
4. **冲突**：同层同名工具互斥；本机无冲突。若以后装其他接管 read/write/edit 的插件，会安装失败并指名冲突工具。风险等级：低。
5. **不解决写规范问题**：PowerShell 管道编码、`.ps1` BOM 规范仍归白皮书第⑥条，插件不代劳。风险等级：无（边界外）。

## 7. 结论与建议

**推荐：采用 `dsh-fs-encoding`，不自研。** 这直接回答「新插件实现成本与可能性」：自研成本高、可能性低（因为已有等价实现）；采用成本极低、覆盖度高。

建议动作（若用户确认）：
1. 备份 profile；
2. `dsh plugin add dsh-fs-encoding`（或按 README 的 npm 方式安装），重启 DSH；
3. 用 5 类样本做读→改→读验收，记录 SHA256 与编码；
4. 决定是否开 `autoGuessEncoding`；
5. 验收通过后，P1 结项。

若用户坚持「要自己的插件」：走 C（post-execute 兜底）最小实现，只覆盖读失败路径，预计 2–4 人日；但需先验证 `tools/post-execute` 能否替换失败结果，否则退回 D。

- [ ] UTF-16LE 带 BOM：read 自动识别，内容正确
